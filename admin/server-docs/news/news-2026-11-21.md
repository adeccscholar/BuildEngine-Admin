## Ceres Solver and external Google libraries

Added independently managed dynamic-package configurations for [gflags 2.3.1](https://github.com/gflags/gflags/releases/tag/v2.3.1) and [glog 0.7.1](https://github.com/google/glog/releases/tag/v0.7.1). Ceres Solver 2.2.0 now declares glog, gflags and Eigen 5.0.1 dependencies. The initial backend uses EigenSparse; SuiteSparse, CXSparse, LAPACK and CUDA are disabled until separate native and licensing evidence is available. Ceres 2.3 removed glog/gflags in favor of Abseil, so 2.2.0 was deliberately selected for this experiment.

Independent installed-package consumer smokes were created for flags parsing, native logging and numerical nonlinear least-squares convergence. **All are pending a real bcc64x run.** Eigen 5 API and legacy CMake Eigen3 discovery require particular verification.

## OpenEXR and independent codec/math components

Registered [Imath 3.2.3](https://github.com/AcademySoftwareFoundation/Imath/releases/tag/v3.2.3), [OpenJPH 0.33.0](https://github.com/aous72/OpenJPH/releases/tag/0.33.0) and [OpenEXR 3.5.4](https://github.com/AcademySoftwareFoundation/openexr/releases/tag/v3.5.4) as independent dynamic packages with direct XML dependency edges. OpenEXR also depends on managed libdeflate 1.26. Initial configurations disable example applications, Python bindings and unnecessary tools.

The upstream source can fall back to bundled dependencies when an external CMake target cannot be resolved, even with FORCE_INTERNAL disabled. This must be audited during the next configure run; a bundled fallback is not accepted as successful externalization. OpenJPH 0.33.0 has a documented CMake Threads/version edge case, handled upstream by OpenEXR 3.5.4 but not yet tested here.

Consumers were added for Imath numerical primitives, OpenJPH linkage and an OpenEXR image-header object. Codec round-trip tests, malformed image tests and provenance verification remain open.

## Parallel Ceres 2.3 Abseil development snapshot and first native build feedback

An additional Ceres Solver 2.3.0 source snapshot was registered from the immutable upstream commit [c39d3cdced6051690c7992ade0f6566fa822ccd2](https://github.com/ceres-solver/ceres-solver/commit/c39d3cdced6051690c7992ade0f6566fa822ccd2). The upstream source declares version 2.3.0, but no official 2.3.0 release tag exists. This is **not a release claim**. Both 2.2.0 and 2.3.0 are retained: the former uses glog/gflags and the latter independently consumes managed Abseil 20260817.0. Each has a separate numerical consumer smoke.

The first native build report confirmed successful Release/Debug compilation of gflags, Imath and OpenJPH, and successful Imath/OpenJPH installations. gflags installation failed because upstream Windows CMake ignored the requested versioned library directories. A version-bound upstream patch now selects isolated Release and Debug runtime/library/config installation directories. Ceres and glog consumer search paths were reconciled.

Installed Imath and OpenJPH consumers now select the explicit versioned CMake export locations. Managed Eigen 5.0.1 gained an installed header-only Eigen3 CMake interface target needed by the Ceres consumers. The OpenEXR audit still correctly blocks a build that did not confirm external OpenJPH, and now surfaces cache evidence for diagnosis instead of masking the fallback. There is no verified follow-up native run yet, so these integrations remain **pending native smoke**.


## A solver, a camera, and a high-dynamic-range laboratory: native BCC64X validation

The end-of-day integration work moved beyond successful compilation and into independent native installed-package consumer verification:

- **[Ceres Solver 2.3.0](/library/ceres-solver/2.3.0/):** Debug and Release native DLLs, installation, publication and documentation passed. Its C++23 consumer solved a nonlinear least-squares problem and passed the numerical `SMOKE|CHECK` assertions. The pinned upstream source is an **unreleased development snapshot**, commit `c39d3cdced6051690c7992ade0f6566fa822ccd2`, not an official 2.3.0 release.
- **[OpenEXR 3.5.4](/library/openexr/3.5.4/):** Debug and Release builds, installation, publication and Doxygen passed. The native installed-package consumer completed with `smoke:consumer:Release PASS` and `ready PASS`. External Imath, OpenJPH, libdeflate and zstd discovery was enforced rather than replaced with bundled fallbacks.
- **[Ceres Solver 2.2.0](/library/ceres-solver/2.2.0/):** The legacy glog/gflags-based integration exposed a real Windows C runtime portability problem in public Bessel wrappers. A version-bound source patch uses `_j0`, `_j1` and `_jn` without removing automatic differentiation or Schur specializations. The independent smoke then exposed a separately corrected mismatch between `ceres-consumer.exe` and the executable named by the XML consumer contract. Final acceptance is recorded as operator-reported, without inventing a missing final 134/134 log.

Ceres 2.2.0 is retained but marked **superseded by 2.3.0**. This catalog relationship is not deletion, does not alter existing dependency pins, and does not convert the pinned 2.3 development snapshot into an upstream release. The source, CMake target, package export, native runtime and smoke gates remain separate pieces of integration evidence.

### Extended demonstration: HDR Photon Observatory

A new native Windows application combines the current Ceres package, OpenEXR, Imath, Eigen, SDL2 and Dear ImGui. It generates real floating-point high-dynamic-range light fields, serializes them through the installed OpenEXR API, and runs actual Ceres nonlinear least-squares calibration for a synthetic sensor response. The operator can inspect its HDR preview, target versus fitted samples, solver iterations, exposure and tone mapping. An independent `--verify` path checks numerical convergence and file round-trip accuracy. This application is separately labelled **not verified** until native CMake, CTest and GUI execution pass; a successful library FSM does not validate a newly written showcase.

### Book-page dewarping for OCR

The existing [Tesseract OCR Studio](/showcase/graphics/tesseract-ocr-studio/) already uses OpenCV perspective correction for flat pages. Curved book pages require a nonlinear resampling map. A new manually adjustable page-curvature mode uses OpenCV's real `remap` to straighten page text lines before Leptonica and Tesseract, preserving frozen-frame OCR and a visible unmodified source. The preview makes the correction inspectable, while an independent synthetic geometry test verifies measurable straightening. Automatic physical surface recovery from a single image remains a separate research problem; a curved page is not correctly reconstructed by a four-corner homography alone.
