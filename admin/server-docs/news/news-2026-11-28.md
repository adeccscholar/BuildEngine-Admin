**Operator-reported milestone:** the C++Builder 13 BCC64X integration now completes on both the full developer workstation and the reduced Windows Server 2025 production machine. The active November 28 XML catalog contains **118 distinct library IDs and 154 retained version records**, including superseded versions. This report does not claim to have independently executed the production clean-room run; the operator confirmed its outcome. ## Why this mattered

The objective was not simply to compile a collection of Microsoft headers. We wanted a reproducible native C++23 library ecosystem that can support accelerated OpenGL visualization and real Direct3D 12 applications while continuing to use the Embarcadero BCC64X toolchain. The two clean-room environments expose hidden dependencies: the developer workstation contains a large tool inventory, while the virtual Windows Server 2025 runs with the pinned Windows SDK, C++Builder 13 and managed CMake/build tools. An integration that depends accidentally on Visual Studio or a local SDK cannot be considered portable.

## Up and down: 22–28 November

### Source, ABI and compiler

Windows SDK headers and native BCC64X types exposed assumptions made by upstream MSVC and Windows-only projects. DirectX-Headers required a real DXCore adapter factory rather than a success-returning stub. Detours needed selective source compatibility; C++/WinRT needed generated projections, native COM signatures and isolated Windows Runtime test headers. Toolchain substitutes, general-purpose Python glue, TAEF and implicit Visual Studio paths were rejected by the project rules.

### DXC: old test ecosystems versus actual compiler behaviour

A substantial amount of time went into legacy ATL/WEX/TAEF and DIA dependencies. The project distinguished the actual DXC compiler and native COM ownership from test harness and debug-only components. Separate managed SPIR-V packages and the DXC runtime path were essential, while multi-hour Doxygen processing revealed a documentation scaling problem. The lesson was to test observable compiler behaviour directly and to separate expensive documentation from compilation feedback.

### DirectXTK12: shader tools to a complete consumer

After resolving the managed DXC runtime, the source build exposed an implicit Windows.Gaming.Input selection despite a requested XInput path. Fixing the input choice revealed a Windows `Interlocked` pointer ABI mismatch in XAudio one-shot counters. Building a native shared DLL then required explicit XInput imports and a COFF import library for the Windows XAudio2 2.9 system DLL, generated with the managed LLVM linker. The final package smoke exposed a doubled include prefix in `SpriteBatch.h`, not a defect in DirectXTK12 itself. Both configurations subsequently reached build/install/metadata/publish and the package smoke passed on the developer workstation.

### Production-server finish: English strings are not Windows contracts

The production VM still failed C++/WinRT Catch2 assertions comparing `HRESULT` fallback messages to English literals. The original upstream test repeats these literals in multiple paths. A partial version-bound test patch fixed only some occurrences. A source-level verification gate exposed the remaining ones before expensive CTest execution, after which the complete locale-dependent set was patched. The functional checks on HRESULT identity, exception type and intentionally supplied messages remained. The final success on the production machine was reported by the operator; no tests were disabled to hide the problem.

## 28 November: the GPU execution barrier finally fell

The first DirectX Prism GPU validation initially failed after compiling the GLSL shader: the application created an OpenGL context, issued a draw call, but never returned from `glFinish()`. Separating the UI renderer, timer query and 16 × 16 constant-colour shader established that the problem was not ray-marching complexity or ImGui. The managed Mesa D3D12 path lacked an available `DXIL.dll` validator runtime. BuildEngine now pins the official Microsoft DXIL validator 1.9.2609 as an independent shared-runtime package with exact source hash, license and managed Release/Debug output. The native Windows DXGI Mesa code also needed a version-bound adapter-selection patch: an explicit GPU request now takes priority over the automatically selected integrated adapter, without silently falling back.

**Operator-provided native results from DirectX Prism, Mesa 26.2.1, Windows / BCC64X:**

| GPU / selected adapter | OpenGL / GLSL | GPU timer samples | Median GPU pass | P95 GPU pass | Result |
| --- | --- | ---: | ---: | ---: | --- |
| Intel UHD Graphics / Intel | 4.1 / 4.10 | 105 | 5.062 ms | 5.524 ms | Benchmark PASS |
| NVIDIA RTX 4000 Ada Generation Laptop GPU / NVIDIA | 4.6 / 4.60 | 210 | 0.157 ms | 0.162 ms | Benchmark PASS |

The **ratio of the reported medians is 32.24×** (5.062 / 0.157); the P95 ratio is approximately **34.10×** (5.524 / 0.162). Both explicitly selected GPU paths passed the independent shader-readback probe, the full 30-frame OpenGL/ImGui/WGL verify, and the benchmark with exit code 0. The NVIDIA probe returned the expected constant colour (RGBA 64,127,191,255); the Intel probe returned (64,128,191,255), both within the defined pixel tolerances. The earlier Intel 30-frame verify reported a last GPU pass of 2.470 ms, and NVIDIA reported 0.052 ms: these are single verification observations, **not** the controlled benchmark medians.

**Scope of the claim:** the timings measure asynchronous OpenGL GPU shader-pass duration on one operator workstation, not complete frame latency, application throughput or a universal Intel-versus-NVIDIA performance factor. Different sample counts, GPU clocks, frame sizes, driver states and presentation loads constrain comparison. No Zink/Vulkan result has yet been measured, and no NVIDIA-versus-Intel claim is made for the other showcases. Zink may translate OpenGL to Vulkan using the installed NVIDIA Vulkan driver, but requires a separately verified device selection, rendered-frame acceptance and identical-workload benchmark.

This milestone demonstrates why precise PE import closure and source-pinned runtime dependencies matter: merely compiling DirectX Headers and DXC did not guarantee that Mesa could submit and validate executable GPU work. The runtime package and DXGI patch completed the missing bridge. The developer workstation result does not establish GPU access on the headless production VM.

## Architecture decisions that survive the week

- **BCC64X only:** no fallback to MSVC/MinGW, no unplanned Windows Kits header contamination
- **Dynamic runtime and DLL products:** import libraries are link artifacts, not static product replacements
- **Reproducibility:** patches are pinned to upstream versions, and changed contracts advance their UTC library timestamp
- **One main branch:** no feature branches or pull requests
- **Precise diagnostics:** archive all technical output, keep console errors in the deduplicated heartbeat section
- **Two physical test environments:** full workstation and reduced production VM both matter
- **Independent showcase evidence:** a successful managed-library smoke is not proof that a graphics application reaches the GPU

## From integration to visible proof

Existing OpenGL showcases already have managed Mesa, GLEW, official ImGui OpenGL3 rendering and experimental Gallium D3D12 selection. New demonstrations should make the Microsoft stack tangible without misrepresenting which computation runs on the GPU. Two native application source contracts are now committed to BuildEngine-Tests: **[DirectX Prism](/showcases/)** uses actual DirectXMath matrices, original Mesa OpenGL ray marching, a deferred GPU timer and a bounded comparative `--benchmark-gl`; **[DXC Shader Foundry](/showcases/)** invokes the managed `IDxcCompiler3` to compile real Shader Model 6 HLSL to DXIL while separately rendering an original GLSL visualization. Both projects contain independent CMake builds, headless verification, F1/F11 desktop behavior and clearly labelled conceptual gallery tiles. **Mesh Aurora / DirectXMesh** and **Texture Observatory / DirectXTex** remain proposed next applications, not yet implemented. Native Direct3D 12 graphics must use an actual D3D12 device and command queue; Mesa D3D12-over-OpenGL experiments are separately measured and identified.

The acceptance matrix records the *requested* backend, *actual* GL/D3D adapter and driver, mode, resolution, compute time, frame time, screenshot hash and verified smoke/check status. Concept illustrations do not substitute for native captures. DirectX Prism has since passed native BCC64X GPU verification and benchmark runs on the operator's Windows workstation; DXC Shader Foundry remains **[not verified]** until its own native acceptance. The full XML snapshot was also reconciled into 152 version-specific migration guides and 152 historical versioned library rows; the subsequent DXIL validator package is newly registered, without modifying producer contracts.

## Verified Mesa D3D12 acceleration: the missing DXIL runtime and two physical GPUs

The November 28 workstation investigation progressed from failed PE import closure to native GPU evidence. The managed Mesa 26.2.1 `libgallium_wgl.dll` imported `DirectX-Guids.dll`, which required an explicit DirectX-Headers package root in the showcase's staged closure. The more consequential runtime fault appeared at the first `glFinish()` following a shader draw: context creation, shader compilation and `glClear()` alone had succeeded, but GPU execution failed. A dedicated, version-pinned `dxil-validator@1.9.2609` package now provides the official Microsoft `DXIL.dll` with verified archive hash and license. With the DLL staged, the minimal shader, GPU synchronization and exact RGBA8 pixel readback all passed.

A second defect prevented adapter selection. The native Windows Mesa DXGI path selected a WGL-provided LUID or the first adapter instead of honoring `MESA_D3D12_DEFAULT_ADAPTER_NAME`. A version-bound Mesa 26.2.1 patch now matches explicit hardware adapter names through DXGI and fails instead of silently falling back to Intel. Both Intel UHD Graphics and NVIDIA RTX 4000 Ada Generation Laptop GPU were independently selected and verified on the same workstation.

### DirectX Prism: operator-measured GPU pass durations, 28 November

| Metric | Intel UHD Graphics | NVIDIA RTX 4000 Ada Laptop GPU |
| --- | ---: | ---: |
| Mesa D3D12 | PASS | PASS |
| OpenGL / GLSL | 4.1 / 4.10 | 4.6 / 4.60 |
| 30-frame GPU + ImGui + WGL verification | PASS | PASS |
| Benchmark samples | 105 | 210 |
| Median GPU pass | 5.062 ms | 0.157 ms |
| 95th percentile GPU pass | 5.524 ms | 0.162 ms |
| Benchmark process exit | 0 | 0 |

The median GPU-pass duration on NVIDIA is **32.24 times shorter** than on Intel; the 95th-percentile ratio is **34.10**. These ratios compare completed OpenGL timer-query measurements for the DirectX Prism shader workload, not total frame duration, CPU-to-GPU speedup or generally applicable graphics-card performance. The sample counts differ, and a paired, controlled benchmark series remains a separate task. The independent minimal NVIDIA readback produced RGBA `(64,127,191,255)` and passed.

**What is verified:** named-device selection, actual hardware renderer identity, real shader execution, GPU synchronization, ImGui drawing, WGL swap, and the instrumented benchmark on both physical GPUs. **What is not verified:** Mesa Zink/Vulkan performance. The active Mesa package explicitly enables only `softpipe,d3d12`; Zink requires a separately validated build contract and Vulkan runtime. The earlier claim that DirectX Prism had not been tested is superseded by the operator-provided native logs above.

## GPU backend controls across the showcase gallery

The managed Mesa SDL2/ImGui OpenGL applications now share a restart-safe Gallium backend dropdown, a separate DXGI device dropdown and an asynchronous GPU-pass timing caption: DirectX Prism, Tensor Nebula, DXC Shader Foundry and Navigation Reactor. Three existing SDL2 native OpenGL viewers (OpenGL SDL2 Earth, OpenMP Galaxy and GeoSpatial terrain) now use native Win32 comboboxes and explicitly managed Mesa/DirectX-Headers/DXIL runtime staging. Their new desktop integration is **[not verified]** pending per-project BCC64X builds and visual checks. The independent Skia/GDI viewer is not OpenGL. VTK 9.7.2's existing system-OpenGL path has not been silently replaced with Mesa; a VTK-specific runtime validation is required before adding a selectable Mesa backend.

On all these applications the window title reports the most recently completed GL timer-query draw pass, not an invented cross-showcase benchmark or full CPU+GPU frame time. When the GPU timer has no completed sample the title says that the measurement is pending. The managed Mesa 26.2.1 package was built with `softpipe,d3d12` only. Zink/Vulkan is listed as unavailable; no Vulkan hardware benchmark has been measured.

## Managed Vulkan/Zink integration: source contract updated, desktop result pending

The BuildEngine catalog now defines **118 distinct library IDs and 154 version records**, including the new pinned `vulkan-loader@1.4.368` dependency on `vulkan-headers@1.4.368`. The loader is built as a BCC64X-native dynamic `vulkan-1.dll` with the Embarcadero resource tool and no MSVC/MASM fallback. The `opengl@26.2.1` Meson contract now requests `-Dgallium-drivers=softpipe,d3d12,zink`, uses only managed header/import-library paths, and stages `vulkan-1.dll` explicitly with each updated OpenGL showcase. The Zink UI is experimental, and its Vulkan device selection is currently automatic only; a D3D12 DXGI adapter-name override is **not** a Vulkan device-select policy.

**State boundary:** These are committed source/build contracts, **not verified Vulkan output**. No BCC64X Mesa-Zink build, NVIDIA Vulkan ICD selection, shader correctness test or Vulkan benchmark has yet been observed. The already verified Intel and NVIDIA **D3D12** measurements remain separate. The interactive titles now use a rolling arithmetic mean of the latest 64 completed GPU operations; switching backends starts a new process with a fresh measurement window. oneTBB replaces the old dedicated numerical worker in Tensor Nebula; full OpenGL context separation for Softpipe is a further native acceptance task.

VTK 9.7.2 already links against the managed Mesa import library. Its previous showcase excluded the Mesa runtime DLL and used system OpenGL. An **opt-in** `VTK_ENABLE_MANAGED_MESA` CMake mode now stages the managed Mesa, DXIL, DirectX-Headers and Vulkan loader closure without changing the system OpenGL default. Renderer provenance, GPU volume rendering, screenshots and native interaction must pass before the VTK graphics provider can be switched by default.
